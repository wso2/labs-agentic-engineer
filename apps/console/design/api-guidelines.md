# Console API guidelines

How the console talks to the `aep-api` BFF. Three rules are non-negotiable;
the rest is per-feature judgment with a promotion path (see Error handling).

## Client

- All requests go through the **`openapi-fetch` client** in `src/api/client.ts`,
  typed with `paths` generated by `openapi-typescript` from
  `packages/contracts/api/v1/openapi.yaml` into `src/generated/aep-api.d.ts`
  (the console's `gen` script; turbo runs it before build/typecheck). No raw
  `fetch` to BFF endpoints anywhere in feature code.
- The contract's paths are **unprefixed** (`/projects`); its `servers` base
  `/api/v1` is applied via the client's `baseUrl` — never write `/api/v1` in
  a call site.
- Request/response types come from the generated client. Never redefine or
  "helpfully widen" them locally — drift is a compile error by design.
- Contract changes are proposed **frontend-first** when UI needs them: edit the
  OpenAPI, `make gen`, build against the new types (see
  `development-flow.md` step 4).

## Server state: TanStack Query

- Every read is a `useQuery`, every write a `useMutation`, wrapping the
  generated client. No server data in `useState`/`useEffect`.
- **Query keys** are structured arrays owned per feature:
  `['projects', projectId, 'tasks', filters]`. A feature exports its key
  factory from `features/<feature>/api/keys.ts`.
- **Invalidation:** mutations invalidate the narrowest affected keys in
  `onSuccess`. Optimistic updates only where the feature issue's decisions
  comment called for them.
- **Retries:** default retry (3, exponential backoff) for queries; **no
  automatic retry for mutations** — a failed write is surfaced, not silently
  repeated.
- **Staleness:** default `staleTime` 30s for lists, longer for near-static
  reference data. Real-time surfaces use SSE (see the agents SSE contract in
  `@aep/contracts`), not polling.

## Error handling & user feedback

**Three non-negotiables** (brutal to retrofit, so fixed from day one):

1. **No raw `fetch`.** Every BFF call goes through the generated client +
   TanStack Query. No exceptions in feature code.
2. **Every view ships empty / loading / error states.** They are part of the
   feature's design, and mocks must be able to produce all three (see below).
3. **Exactly one global 401 handler** → re-auth flow. Features never handle
   auth errors themselves.

**Everything else is per-feature judgment** — toast vs inline, retry
affordances, skeleton styles, confirmation dialogs. Guiding principles, not
rules:

- Acknowledge async actions quickly (pending state on the control, not a
  frozen UI).
- Errors surface where the user's attention is: near the field for
  validation, in the region for load failures, non-blocking for background
  work.
- Prefer a visible state change over a success toast.

**Promotion rule:** when a pattern proves out in a shipped feature, promote
it into this document as a convention (with a pointer to the feature issue), so later
sessions converge on it instead of re-inventing. This section is expected to
grow.

## Mock layer (MSW)

The console is fully developable without a backend.

- **Mechanism:** [MSW](https://mswjs.io) intercepts the generated client's
  requests in the browser. App code is identical in mock and real mode.
- **Location:** `src/mocks/` — `handlers/<feature>.ts` + `fixtures/`.
- **Typed against the contract:** handlers and fixtures import the generated
  OpenAPI types, so a contract change breaks mocks at typecheck time, not in a
  demo. Hand-rolled untyped JSON fixtures are forbidden.
- **Scenarios, not just happy paths:** each feature's handlers expose its
  error and empty scenarios (e.g. via a scenario switch in fixtures) so the
  states in the doctrine above can be built and tested.
- **Mode switch:** `VITE_API_MODE=mock` enables MSW in dev. Mock code is
  dev-only — excluded from production builds (dynamic import guarded by the
  flag; verify with a bundle check).
- **Testing:** Playwright/component tests run against mocks. Running the
  feature against the real BFF on the local setup *is* the ship validation,
  and it happens before the merge (`development-flow.md` step 7).
