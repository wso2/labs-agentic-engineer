# P3.5 — Cross-project access requests (design)

> Marketplace phase P3.5 (plan.md §8). Builds directly on P3 (org-service +
> catalog) and the declarative-wiring refactor (org-service gate, issue-comment
> resolution, provider-publish via `exposesAPI.orgPublished`). Status: DESIGNED.

## Problem

A consumer's design references an org service that **exists but is published
only at `project` visibility** — so the catalog returns `namespaceVisible:false`,
`resolveOrgServices` marks the dependency `unresolved`, and the consumer's
component sits **On Hold** forever (the Phase-A `orgServiceGates` gate never
releases). Today there is no way for the consumer to ask the provider to publish
it cross-project. P3.5 adds a **provider-approved, cross-repo, stateful** request
flow that turns that dead-end into an actionable handoff.

## Key decisions (resolved during brainstorming)

1. **Provider-approved, via a GitHub task on the provider's repo** — not
   auto-published, not an in-console inbox. Respects cross-team ownership and
   reuses the existing GitHub-driven task model.
2. **Granting = a coding-agent task** that re-writes the provider component's
   `workload.yaml` to add `namespace` visibility (the existing provider-publish
   agent path). Provider approval == **dispatching that task on their board**.
3. **`exposesAPI.orgPublished:true` is set as a durability side-effect** when the
   publish task completes — NOT pre-flipped at request time (so nothing in the
   provider's design changes without their consent). Rationale: a future
   re-implementation of the provider component regenerates `workload.yaml` from
   the design; without `orgPublished` the `namespace` line silently reverts and
   the consumer breaks. `orgPublished` is the durable record in the source of
   truth.
4. **State home = a lightweight `AccessRequest` record**, not derived on the fly.
5. **Functional resume is the existing gate, not the AccessRequest.** Once the
   provider is namespace-visible, `orgServiceGates` releases the consumer on the
   next sweep regardless of P3.5. The `AccessRequest` is the **tracking/UX layer**
   — it gives the consumer visibility and drives the request action; it is not on
   the critical path for the consumer resuming.

## End-to-end flow

```
Consumer design view                Provider project                 Consumer
─────────────────────               ────────────────                 ────────
org-service dep = `unpublished`
(catalog: name exists,
 namespaceVisible:false)
        │
   [Request access]  ───────────▶  ComponentTask + GitHub issue
   AccessRequest{requested}        "Publish <comp> org-wide:
                                    add namespace visibility"
                                            │
                                    provider DISPATCHES (= approval)
                                    agent adds `namespace` → PR → merge
                                    → deploy; orgPublished:true set
                                            │
                                    catalog: namespaceVisible:true ◀──┐
                                            │                          │
   AccessRequest{granted},                 └──▶ orgServiceGates releases
   issue closed                                 consumer component
                                                auto-dispatches (existing)
```

## Components / changes

### 1. Requestable detection — split `unresolved`
`internal/feature/artifacts/artifact_store.go resolveOrgServices`: today marks an
org-service dep `resolved` | `unresolved`. Split the negative case using the
catalog:
- endpoint name exists in the catalog but not namespace-visible → status
  `unresolved`, **reason `unpublished`** (requestable).
- no endpoint with that name → status `unresolved`, **reason `not-found`** (not
  requestable; surfaced as a plain warning / typo hint).

Needs a catalog method `ExistsAnyVisibility(ctx, orgHandle, name) bool` (or extend
`ResolveNamespaceVisible` to also report "exists but project-only"). The
dependency gains an explicit **`reason`** field (string enum: `""` | `unpublished`
| `not-found`) alongside `status`, serialized to the design view — `models.Dependency`
+ the artifact-store frontmatter round-trip + the agents-service Zod schema (mirror
how `status` is carried).

### 2. The request action (cross-project)
New BFF endpoint, e.g. `POST /api/v1/organizations/{org}/projects/{consumerProj}/components/{comp}/access-requests` with body `{ orgServiceName }`. It:
1. Resolves the **provider** project from the catalog row (`WorkloadEndpointInfo.Project`)
   → its repo via `repoService.GetRepo(org, providerProject)`.
2. Idempotency: if an open `AccessRequest`/publish-task already targets
   `(providerProject, providerComponent)`, reuse it (multiple consumers → one
   provider task, many `AccessRequest` rows).
3. Creates a **publish ComponentTask** on the provider project + its GitHub issue
   on the provider's repo (reuse `issueService`/`CreateIssue(owner, repo, …)`),
   labelled `access-request`. This is a **targeted modification** of an
   already-deployed component, so it uses a **purpose-built issue body** (NOT the
   standard `BuildIssueBody` — that one is driven by `ResolveOrgPublished`, which
   is still false): the body tells the agent to clone the repo, add `namespace` to
   `<appPath>/workload.yaml`'s endpoint `visibility`, and open a PR — a one-line
   edit to existing code, which the `asdlc` skill already supports (the workspace
   is a clone with the existing files). Modeled as a ComponentTask with a new
   `Type`/marker (e.g. `org-publish`) so the board + lifecycle treat it normally
   but the issue body + completion hook know it's a publish.
4. Writes the `AccessRequest` row (status `requested`).

### 3. Data model — `AccessRequest`
```
AccessRequest {
  ID
  OrgID
  ConsumerProjectID
  ConsumerComponentName
  OrgServiceName               // = provider OC component name (catalog key)
  ProviderProjectID
  ProviderComponentName
  ProviderTaskID               // the publish ComponentTask
  ProviderIssueNumber/URL
  Status                       // requested | in_progress | granted | rejected
  CreatedAt, UpdatedAt
}
```
GORM table; migrated like the other feature tables. One row per
(consumer-component, org-service); a unique-ish index on
(OrgID, ConsumerProjectID, ConsumerComponentName, OrgServiceName).

### 4. Provider publish task + `orgPublished` durability
- The publish task flows through the normal lifecycle
  (pending→in_progress→…→deployed). Its issue body explicitly instructs the
  `namespace` visibility addition (purpose-built; does not rely on `orgPublished`
  being set yet).
- **On the provider task reaching `deployed`** (the cascade `OnTaskDeployed` for
  that component), set `exposesAPI.orgPublished:true` in the provider design
  (durability) — idempotent.

### 5. Status sync
Driven off existing signals (no new watcher if avoidable):
- provider task dispatched → `AccessRequest.in_progress`.
- provider component `deployed` AND catalog `namespaceVisible:true` → `granted`;
  close the provider issue; (the consumer gate auto-releases independently).
- provider issue closed without merge / task `rejected` → `AccessRequest.rejected`.
Hook points: the dispatch cascade `OnTaskDeployed` (grant) and the existing
GitHub webhook handlers (issue closed / PR closed-unmerged → rejected). The
consumer design view reads `AccessRequest.Status` + live catalog to render the
chip.

### 6. Consumer design-view UX
On an `unpublished` org-service dep: a warning + **Request access** button. After
requesting: a status chip `access requested · pending` → `granted` → `denied`,
with a link to the provider issue. No new page — extends the existing dependency
resolution cards.

## What is reused (not built)
- The org-service **gate** + auto-dispatch (Phase A) — the functional resume.
- The provider-publish **agent path** (orgPublished → namespace visibility) — P3.
- ComponentTask + issue + dispatch + webhook lifecycle — P1/P2.
- `CreateIssue(owner, repo, …)`, `GetRepo(project)`, the catalog.

## Error handling / edge cases
- **Duplicate requests** (multiple consumers, same provider endpoint): dedupe to
  one provider task; N `AccessRequest` rows; all flip `granted` together.
- **Provider rejects** (closes issue / closes PR unmerged): `AccessRequest.rejected`;
  the consumer sees "denied" + may re-request later.
- **Provider unpublishes later** (orgPublished→false, redeploy): the catalog drops
  namespace visibility → the consumer's gate re-holds on the next sweep (existing
  behaviour); a prior `granted` AccessRequest is stale — surface the dep as
  `unpublished` again from the live catalog (catalog is authoritative over a stale
  AccessRequest).
- **`not-found`** target: no request affordance; plain "unknown org service" warning.
- **Cross-project auth**: any org member may request; the provider's dispatch is
  the authorization boundary. (No finer RBAC in P3.5.)

## Testing
- Unit: `resolveOrgServices` reason split (`unpublished` vs `not-found`) against a
  fake catalog; `AccessRequest` idempotency/dedupe; status-sync transitions.
- E2E (test-scenarios.md, new/extended scenario): provider deploys a service
  **project-only** (no `orgPublished`); a second project's component depends on it
  → design view shows `unpublished` + Request access → request creates the provider
  task/issue → dispatch+merge+deploy the provider publish task → catalog flips
  namespace-visible → consumer component auto-dispatches → cross-project call works;
  AccessRequest ends `granted`, issue closed.

## Out of scope (P3.5)
- Per-consumer / scoped visibility (publishing is org-wide, binary).
- Protected (auth'd) org-service targets (P5).
- Finer cross-project RBAC / approval roles.
- Conversational/inbox UX (the request is a button + a GitHub issue).
